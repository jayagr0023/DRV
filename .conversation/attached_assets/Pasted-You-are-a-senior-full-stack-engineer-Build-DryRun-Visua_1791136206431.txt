You are a senior full-stack engineer. Build "DryRun Visualizer" v1: a web app where a student pastes or edits JAVA code plus optional stdin, clicks Visualize, and steps through the real execution with a visual display of code, variables, call stack, heap objects, and output.

Positioning: "See exactly what your code does, one step at a time." Primary user: a first or second year CS student stuck on loops, recursion, references, or object behaviour. Every design choice favours clarity for a beginner.

## 0. Scope
IN v1: Java only, dry run only, rule-based explanations, example library, single-thread tracing.
OUT of v1 (do NOT build, but leave the extension seams in section 3): expected-output comparison, test cases, first-divergence detection, hints/misconception flags, AI explanations, shareable links, accounts or history, other languages, multithreaded tracing, GUI/network/file programs.

## 1. Fixed decisions
- JDK 21 (full JDK with jdk.jdi). The tracer is written in Java using JDI with the launching connector; the debuggee runs in a separate JVM.
- Orchestrator API: Python 3.11 + FastAPI. A separate runner-service starts sandboxed runs.
- Frontend: React + TypeScript + Vite + Tailwind + CodeMirror 6 + Zustand. Diagrams: custom SVG.
- Source analysis for explanations: JavaParser.
- `docker compose up` starts everything.
- A UI reference prototype is provided at docs/reference/prototype.html. Match its look and interaction. It contains a mini in-browser interpreter that is a stand-in only: do NOT port or ship it. All real data comes from the API.

## 2. Language-agnostic runner contract
- A runner image receives one job as JSON on stdin: {schemaVersion, language, code, stdin, limits}.
- It streams NDJSON on a dedicated channel, flushed per line: one "meta" line, then one "step" line per step, then one "end" line {status: ok | compile_error | runtime_error | truncated | timeout, diagnostics[]}. Streaming is mandatory so a timeout or crash still returns the partial trace.
- The backend keeps a LanguageAdapter registry: {id, displayName, version, runnerImage, fileExtension, starterTemplate, examples[], limits, validate(code)}. GET /api/languages is generated from it. The frontend dropdown and editor mode are driven by it (only Java appears now).
- Language-specific data lives only in an optional "meta" field, never in core fields.

## 3. Extension seams (build the interfaces now, ship only the v1 implementation)
These exist so later versions are additions, not rewrites.
1. **Trace document**: the finished result is one immutable "TraceDocument": {traceId (SHA-256 of language + code + stdin + schemaVersion), schemaVersion, language, languageVersion, createdAt, source, stdin, meta, steps, annotations, end}. The same input gives the same traceId. (v1.5 sharing builds on this.)
2. **TraceStore interface** (backend): put(doc), get(traceId). v1 ships a NoOpTraceStore only. (v1.5 adds a real store plus GET /api/trace/{id}.)
3. **Explainer interface**: explain(step, prevStep, sourceModel) -> string. v1 ships RuleBasedExplainer. Explainers run through a registry so another implementation (AI-grounded, v3) can be added or chosen by config.
4. **Analyzer pipeline**: a list of post-trace analyzers, each (TraceDocument) -> Annotation[] where Annotation = {stepIndex, severity, code, message}. v1 ships an empty pipeline, and the "annotations" array on the document is always present (empty). The frontend renders annotations in the explanation bar and as markers on the slider if any exist. (v2 comparison and hints plug in here.)
5. **Frontend stores**: Zustand slices `trace` (document + reconstructed steps), `playback` (current step, speed, playing), `ui` (mode, panels, theme), and a `session` slice reserved for v2 (expected output, comparison result). Panels read only from selectors, never from raw API data.
6. **Feature flags**: a typed config object (shareLinks, compare, aiExplain), all false in v1, with no UI shown when false.
7. **Schema versioning**: every payload carries schemaVersion. The frontend rejects unknown major versions with a clear message. Document the rule: additive changes = minor bump.
8. docs/ADDING_A_LANGUAGE.md and docs/EXTENDING.md (how to add an analyzer, an explainer, a store, a flag).

## 4. Step schema v1 (single source: TypeScript types + Pydantic + JSON Schema, validated in CI)
Each step:
{ step, event: "line"|"call"|"return"|"exception"|"exit", line, frame:{method,class},
  stack:[{method,class,line,locals:{name:ValueRef}}] (depth cap 50, plus a "stackTruncated" count),
  statics:{"Class.field":ValueRef},
  heap:{objectId:HeapObject},
  stdout: string (new text since the previous step), stderr: string (same),
  changed:[paths of variables/fields/elements changed vs the previous step],
  explanation: string, error: null|{type,message,line,stackTrace[]} }
ValueRef = {kind:"prim",type,value} | {kind:"ref",id} | {kind:"null"} | {kind:"uninitialized"}
HeapObject = {id, type, kind:"array"|"list"|"map"|"set"|"string"|"object"|"boxed", elements|entries|fields, size, truncated?:bool}
- Storage: a full snapshot every 50 steps (keyframes), and deltas between them. Document the exact delta format (JSON-patch-like on stack/heap/statics). The frontend rebuilds any step by applying deltas from the nearest earlier keyframe, in a pure, unit-tested function, so Prev and slider jumps are O(50).
- Show collections LOGICALLY (ArrayList, LinkedList, HashMap, TreeMap, HashSet, ArrayDeque, PriorityQueue, String, StringBuilder, boxed types) via read-only JDI field inspection. Never invoke methods on the debuggee.
- Stable short object IDs ("o1", "o2") mapped from the JDI uniqueID. Caps: 50 elements per collection ("...N more"), graph depth 6, 500 heap objects per step. Detect cycles. Disable GC collection for tracked objects so IDs stay valid.

## 5. Java tracer behaviour (implement exactly)
- Source rules: one file with a class containing public static void main(String[]). Detect the main class by parsing. Save as <PublicClassName>.java (or Main.java if none is public). No wrapping or rewriting of code, so line numbers always match the editor. Packages allowed. No main found -> clear diagnostic.
- Compile with javac -g -proc:none. On failure return diagnostics {line, column, message, severity} and no steps.
- JDI StepRequest (STEP_LINE, STEP_OVER at top level; STEP_INTO only into user-source classes) plus MethodEntry/MethodExit filtered to user classes, so library callbacks into user code (compareTo, lambdas, toString, Runnable) are still traced. Exclude java.*, javax.*, jdk.*, sun.*, com.sun.*. Skip JDK static initialisers, synthetic methods, and bridge methods.
- Trace only the main thread. If other threads start, ignore their events and surface one warning in an explanation.
- Locals: only variables in scope at the current line; hide synthetic names; show declared-but-unassigned as "uninitialized".
- Output sync: the debuggee starts through a tiny launcher that installs auto-flushing System.out/System.err wrappers writing to separate pipes. The tracer drains both on every step event, so each step carries exactly the text emitted since the previous step. Document this.
- Stdin is piped to the debuggee; EOF behaves normally.
- Exceptions: ExceptionRequest for caught and uncaught. Caught shows an "exception" step ("Exception X thrown, caught at line N"); uncaught shows the stack trace in the error banner. Handle StackOverflowError, System.exit (emit an "exit" step with the code), and OutOfMemoryError.
- Limits (configurable): 2000 steps (truncated=true, keep the trace), 10 s total (compile 3 s, trace 7 s, partial trace on timeout), debuggee -Xmx256m, 10 KB output cap, 5 KB stdin, 20 KB code.
- Truncation UX: always say "Showing the first 2000 steps of a longer run". Never present a truncated trace as complete.
- Determinism notice: if the source references Random without a seed, Math.random, System.currentTimeMillis, nanoTime, or Thread, add the meta flag "nondeterministic" and show: "This program uses randomness or time, so this trace shows only this one run."

## 6. Rule-based explanations (beginner wording, no LLM)
- Parse with JavaParser and classify each executed line: declaration, assignment, compound assignment, increment, if, for, while, do-while, return, method call, print, throw, object creation, array access.
- Combine node type + variable diff + the NEXT executed line to infer condition outcomes (a while line followed by a body line = "condition i < 5 is true, so the body runs"; followed by the line after the loop = "false, so the loop ends").
- Examples: "Declared int x and set it to 5", "Called factorial(3) with n = 3", "Returned 6 to factorial(3)", "arr[2] changed from 4 to 9", "Created a new Node (o7)", "Printed 'Hello'", "This for loop adds 1 to i, now i = 3".
- Beginner-friendly wording, short sentences, and always say what changed. Never return an empty string; fall back to a plain description of the diff.

## 7. Sandbox and security (treat code as hostile)
- The public API never mounts the Docker socket. A separate runner-service with a minimal job API is the only component with container privileges, is not internet-reachable, and is documented as the trust boundary (or use gVisor; state the choice and why).
- Each run: a fresh container from a warm pool (the container is destroyed and replaced after use, never reused), no network (the JDI channel must not be reachable by user code; prefer the launching connector over a socket), read-only root FS, small tmpfs workspace, non-root, all capabilities dropped, no-new-privileges, default plus custom seccomp, CPU/memory/pids/file-size limits, hard kill at timeout.
- The tracer and user code run as different OS users; user code cannot read or signal the tracer or the output channel.
- Static pre-check (defence in depth only): reject Runtime.exec, ProcessBuilder, java.net, java.nio.file, java.io.File*, reflection, JNI, System.load, and attach APIs with a clear message. The README states honestly that this is bypassable and the container is the real boundary.
- API: rate limit per IP (20/min), request size validation, language checked against the registry, bounded queue with max concurrency and a clear "busy, retry" response.
- Never log user code at INFO. README section "Known sandbox limitations".

## 8. API
- POST /api/trace {language, code, stdin} -> streams NDJSON per the runner contract; a non-streaming mode returns a full TraceDocument.
- GET /api/languages, GET /api/health.
- Versioned under /api and documented with OpenAPI.

## 9. Frontend behaviour (student-first)
- Two modes. **Edit mode**: the code editor is fully editable (CodeMirror 6, Java highlighting, line numbers, Tab indents, Ctrl/Cmd+Enter = Visualize), with a stdin box below it. **Trace mode**: the editor is read-only and shows the current-line and previous-line markers. A single toggle button switches: "Visualize ▶" in Edit mode, "✎ Edit code" in Trace mode. Editing never loses the user's code.
- Compile errors: an error list under the editor; clicking one jumps to the line.
- Controls: Next, Prev, Play/Pause, speed (0.5x, 1x, 2x), slider, First, Last. Keys: arrows, space, Home/End (disabled while typing in the editor or stdin).
- Panels: Variables (current frame locals + statics; changed values marked with colour AND a label, old value struck through, e.g. "5 → 9"), Call stack (own locals per frame, active frame highlighted, recursion readable), Heap view, Output (stdout/stderr tabs, new text highlighted), Explanation bar, Error banner at the failing step with a "Jump to line" button.
- Heap view (SVG): arrays as indexed boxes with the changed index highlighted and badged; lists/sets as boxes; maps as key-value tables; objects as labelled field boxes; references as arrows from variables to heap objects, so aliasing is obvious (two variables converging on one object, labelled "same object"). Hovering a variable highlights its arrow and target. Auto-detect linked lists (one self-typed field, laid out left to right) and binary trees (two self-typed fields, laid out top to bottom), with a generic graph fallback. Arrows follow layout changes and resizes.
- Example library (dropdown, each with a one-line description of what it teaches): loop, factorial recursion, bubble sort, linked-list reversal, binary-tree traversal, HashMap counting, aliasing demo, exception demo, Scanner input demo, string immutability demo, pass-by-value demo.
- First-run guidance: a short dismissible 3-step tour (write or paste code, press Visualize, use Next). A sample program is preloaded and already visualized on first load.
- States: compiling, tracing (progressive as steps stream in, with a "Tracing... 340 steps" chip), empty, truncated, busy, error, nondeterministic notice. Notices are dismissible inline banners, never modals.
- Reserved, not rendered in v1 (behind feature flags): annotation markers on the slider, a "compare" side panel, a Share button.

Design tokens (define once as CSS variables; support light, dark, and system preference with a manual toggle):

- Background: a very light slate/lavender with two soft radial gradient glows (indigo top-left, pink top-right); in dark mode a deep navy with muted violet glows.
- Cards: translucent "glass" surface with backdrop blur, 1px soft border, 16px radius, soft large shadow, small uppercase section titles with an emoji or icon.
- Primary: indigo-to-violet gradient (#6366f1 to #8b5cf6) for the Visualize and Play buttons, with a soft coloured shadow. The logo uses an indigo-to-pink gradient.
- The code editor panel is ALWAYS dark in both themes (a terminal-like card with three window dots and the file name in its header), with syntax colours: keywords violet, strings green, numbers amber, comments grey.
- Semantic colours, always paired with an icon or text label and chosen to be colour-blind-safe (never colour alone):
  - changed value: amber, "✱ changed" badge, short flash, old value struck through
  - new variable or object: green, "+ new" badge
  - active line/frame: indigo (left bar plus tinted background; a "▶" in the gutter)
  - error: red, "⚠" icon
- Spacing scale 4/8/12/16/24. Panels have a title bar and an internal scroll.

Component details:
- Explanation bar: the most prominent element. Large text, a step-type emoji or icon (declaration, loop, condition, call, return, print, error), a gradient tint with a left accent bar, and a "Step N of M" counter at its right.
- Variables: rows as rounded chips: name, value, badge. A small "in <method>" chip shows the frame. Changed rows are tinted amber; new rows green.
- Call stack: stacked cards, newest on top, each showing method(args) and its locals. The active card has an indigo border and an "← active" label. Cards animate in on call and out on return.
- Heap view: array cells are rounded boxes with an index label below; a changed cell lifts slightly, gets an amber border, and shows "✱ changed". Each object shows "pointed to by: x, y" so aliasing is readable even before arrows are drawn. Arrows are smooth curves with arrowheads.
- Output: a monospace terminal look, with the newest text highlighted briefly.
- Control dock: a floating, rounded, blurred pill centred at the bottom with icon buttons (tooltips with keyboard hints), the slider, a speed select, and a step counter. Slider ticks show annotation markers when the flag is on.
- Motion: 150-250ms transitions; everything respects prefers-reduced-motion (animations disabled when set).
- Empty state: a friendly message, a preloaded sample program, and the 3-step tour. Loading: skeletons plus a "Compiling..." then "Tracing... N steps" chip.
- Accessibility: keyboard navigable, ARIA labels on all controls, aria-live on the explanation bar, visible focus rings, contrast at least WCAG AA in both themes.

Design review deliverable (before wiring the API): a /design route (or Storybook) showing every panel in light, dark, and mobile states with sample trace data, built to match docs/reference/prototype.html.

## 10. Testing and acceptance criteria
- Tracer tests on fixed sample programs against normalised golden JSON (object IDs and addresses replaced by order of appearance). Cover: assignment, loops, recursion, nested calls, aliasing, ArrayList/HashMap, caught and uncaught exceptions, compile error, stdin, step cap, timeout with partial trace, System.exit, StackOverflowError, lambda/comparator callbacks, static fields, the nondeterminism flag, and traceId stability (same input = same id).
- Security tests: file access, network, process spawn, fork bomb, infinite loop, memory bomb, reading tracer files, attaching to the JVM. All fail safely and leave the host untouched. Also verify that a used container is destroyed and never reused.
- Frontend: Vitest for the reconstruct function, stores, mode switching, and controls; Playwright e2e: edit code, visualize, step, see output, see a compile error, see the truncation message, edit again and re-visualize.
- Extension tests: an "echo" stub language, a dummy analyzer that adds one annotation, and a fake explainer. Each must be picked up through its registry with no core changes (proves the seams work).
- Acceptance:
  - factorial(3) shows 4 stack frames at the deepest step with correct locals
  - bubble sort marks the changed indices per swap
  - the aliasing demo shows two variables with arrows to ONE heap object
  - a 10,000-iteration loop returns exactly 2000 steps with truncated=true in under 10 s
  - Prev from step N equals the state reached going forward to N
  - a small program traces within 3 s on a warm pool
  - a dummy annotation appears on the slider when the feature flag is on
  - editing the code and pressing Visualize traces the NEW code (no stale trace)
